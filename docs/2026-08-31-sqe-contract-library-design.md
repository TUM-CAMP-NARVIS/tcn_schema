# A shared SQE contract library in `tcn_schema`

**Status:** design proposal. Nothing in this repository has been changed except
the addition of this file. No CMake, no `conanfile.py`, no IDL, no header was
edited. This file is untracked; review it before it enters history.

**Date:** 2026-08-31
**Branch it was written on:** `feat/sqe-contract-library`

**Peers, read-only:**

- `spatial_query_engine_rs` — the engine. It defines the contract.
- `tcnart` — consumer 1. Plans: `docs/plans/2026-08-30-sqe-0.3.0-migration-plan.md`
  (Phase 1) and `docs/plans/2026-08-31-sqe-client-api-plan.md` (Phase 2).
- `artekmed` — consumer 2. Larger, further behind, and the repo that contains
  all of the existing SIS/SRG code.

**Decision already taken, not re-argued here:** the same SQE integration work
has to be done in two C++ code bases, and it will be done once, in a shared
library, whose home is `tcn_schema`. This document designs that library. §10
states the case *against* it honestly, because a design document that only
argues for its own conclusion is not useful — but it does not reopen the
decision.

## 1. The problem, and the evidence

### 1.1 The duplication is real, and it is lopsided

Message publish/use sites across the two consumers, counted by `grep` over
`src`/`libs`/`apps`/`modules`/`bindings`:

| type | `tcnart` | `artekmed` |
| --- | --- | --- |
| `StreamDescriptorMessage` | 16 | 31 (41 including bindings and headers) |
| `Pose6DMapMessage` | 5 | 9 |
| `TargetTrackingMessage` | 1 | 2 |
| `Pose6DMessage` | 2 | 2 |

`artekmed`'s half is the larger one, and it is also the one that has not
started: `artekmed` pins `tcn_schema/0.1.1@artekmed/stable`
(`libs/pcpd_dependencies/conanfile.py:91`) while `tcnart` pins `0.2.0`
(`tcnart/conanfile.py:116`) and the engine reads `0.3.0`. **Three schema
versions, two consumers, one wire.**

### 1.2 The expensive part is not the message types — it is the rules around them

Every message type either consumer needs is already generated by this
repository. What is *not* in this repository is everything the engine's
documentation calls a contract and the IDL does not express:

- the `application/cdr;Type` encoding string, mandatory, exact-match on the far
  side (B2, B3);
- which of two different identifier alphabets applies to which half of a
  composed id (B30, B39);
- that a relation-stream handle comes from a reply and is never computed (B33,
  B34);
- that the handle's lifetime is shared and does not nest (B36);
- that a concrete-target pose stream carries exactly one item per message;
- that a liveliness token is required or the client is swept (B41).

`artekmed`'s current SIS code
(`apps/pcp_shm_multistream_tracker/src/multistream_tracker.cpp:309-422`) gets
several of these wrong at once: it publishes with a bare
`zenoh::Encoding::Predefined::application_cdr()` and no type annotation, uses
`SISJoinMessage`/`SISComponentMessage`/`SISRelationMessage` types that 0.3.0
deleted, and derives its join key from `m_camera_name` while deriving its
descriptor key from `m_entity_name` — so its client id and its
`stream_descriptor_topic` agree only by configuration accident. B18 records
all of this; none of it is a message-type problem.

### 1.3 Every one of these fails silently

That is the whole argument for baking them into code. The engine's mutation
keys are plain subscribers, not queryables — *"graph mutations answer
nothing"* (`protocol.md` §3, B27). A client that gets any of the rules above
wrong is told nothing at all, by anything, ever. The failure surfaces as a
pose that stops updating, a stream that is `Active` and permanently silent, or
a fragment that was never created.

Two of these have already taken a daemon down or cost a lab session:

- **B39** — validating a client id with the identifier rule instead of the
  fragment rule caused a one-message denial of service against the daemon, for
  every client using the default `tcn/loc/pcpd` prefix.
- **B33/B34** — a computed handle stops nothing and subscribes to a topic
  nothing publishes on. B34's own detection note says the runtime signal is
  now ambiguous with correct B36 behaviour, so *the compile error is the only
  unambiguous signal there is*.

**Design principle for the whole library, stated once:** where a rule has a
silent failure mode, express it as a type or an API shape, not as a comment.
The consumer should be unable to write the wrong thing, or should fail
locally and loudly at compile time or at the call, rather than being dropped
quietly by a daemon it cannot see the log of.

## 2. Two layers, and why the split mirrors the engine

The engine already splits exactly this way and for exactly this reason:
`sqe-core` is a pure actor with no I/O, and a driver binds it to Zenoh. The
same split applies here.

### Layer 1 — `sqe_contract`: the dependency-free contract core

Key construction, encoding strings, identifier validation, status semantics,
handle rules, the one-item-per-message rule, and the local lease arithmetic.
Pure string and type work over the generated `tcnart_msgs` types.

- No Zenoh. No transport. No threads. No I/O of any kind.
- Trivially unit-testable on every platform, including a host build with no
  network stack.
- **This is where nearly every silent failure lives.** B2, B3, B23, B30, B32,
  B33, B34, B36, B39 all resolve to string handling and type discipline.
- Header-only is the right shape: no ABI to keep, no per-platform binary, no
  `dllexport` story on WindowsStore, no visibility mismatch, and an
  `INTERFACE` library adds nothing to a link line it is not asked for.

### Layer 2 — `sqe_transport`: the thin Zenoh binding

The liveliness token, the start → handle → subscribe → status → stop
lifecycle, and the typed query that checks a reply's declared type before
decoding it.

- Needs `zenoh-cpp`, so it is a **separate Conan component behind an option**.
  A consumer that wants only the IDL types must not inherit Zenoh, and today
  neither `tcn_schema` nor any of its ROS 2 components does.
- **Read §10.1 before building this.** The two consumers are on different
  zenoh-cpp versions today, and layer 2 is the part that cannot straddle that.
  This document recommends shipping layer 1 first and holding layer 2 open.

### What belongs in which

| concern | layer | why |
| --- | --- | --- |
| `application/cdr;Type` for a given message type | 1 | pure type→string |
| `valid_id` / `valid_fragment` / topic rules | 1 | pure predicate |
| `{client_id}{SUFFIX}` key construction | 1 | pure string |
| `{fragment}::{name}` composition | 1 | pure string, two alphabets |
| status classification (`Pending` is acceptance) | 1 | pure enum logic |
| reading a handle out of a reply, invariant check | 1 | operates on a decoded struct |
| **local refcount for shared handles** | **1** | pure arithmetic; the single most valuable unit test in the set |
| fragment assembly + origin precondition | 1 | pure validation over `SRGraph` |
| declaring/holding the liveliness token | 2 | Zenoh session |
| the `get` on `/sis/stream/start`, and its timeout | 2 | Zenoh query |
| subscribing `{handle}` and `{handle}/status` | 2 | Zenoh subscriber |

Putting the lease arithmetic in layer 1 is deliberate and is what makes B36
testable with no daemon, no session and no network — see §4.6 and §8.

## 3. What the core may and may not use

The hard constraint is platform reach. `tcnart` builds for **Android,
WindowsStore/UWP, Linux, Jetson (aarch64) and MSVC**, and sets
`CMAKE_CXX_STANDARD 17` with `CMAKE_CXX_STANDARD_REQUIRED TRUE`
(`tcnart/CMakeLists.txt:23-24`). `artekmed` also sets 17
(`artekmed/CMakeLists.txt:28`). `tcn_schema` sets no standard of its own at
the top level; the per-module targets set `CXX_STANDARD 17` individually.

**The core targets C++17 and is written to be compilable by the strictest of
those toolchains.** The rules below are stated rather than implied, because
each one has a platform where violating it fails.

### 3.1 May use

`<cstdint>`, `<cstddef>`, `<cstring>`, `<string>`, `<string_view>`, `<vector>`,
`<array>`, `<optional>`, `<utility>`, `<type_traits>`, `<functional>`,
`<map>` / `<unordered_map>`, `<cassert>`, and the generated `tcnart_msgs`
headers.

`inline constexpr` variables (C++17) are what make the key-suffix and
type-name tables header-only with no ODR problem, so they are used freely.

### 3.2 Must not use, and why

| forbidden | reason |
| --- | --- |
| `<filesystem>` | patchy on older Android NDK; absent or partial on some UWP configurations. The core reads no files at all, so this costs nothing |
| `<cctype>` — `isalnum`, `isalpha`, `tolower` | **the obvious wrong way to write the validators, and it is wrong twice.** First, these functions are **locale-sensitive**: what `isalnum` accepts depends on the process's global locale, which the core does not control and a consumer may change. Second, **the aarch64 trap**: `char` is *unsigned* on ARM and *signed* on x86, and these functions are UB for a negative `int` argument — so a validator written with `isalnum` behaves differently on Jetson and Android from how it behaves on the developer's x86 box. The rule in §4.3 is a fixed ASCII allow-list, so a plain range comparison over `unsigned char` is both correct and sufficient on every target. No Unicode tables, no locale, no `<cctype>` |
| `<locale>`, `setlocale`, `std::stod`, `operator<<` for numbers | locale-dependent formatting. A process running under `de_DE` writes `5,0` where the wire wants `5.0`. Never format a wire value with a locale-aware facility |
| `<iostream>`, `<sstream>` on any path | static-initialisation order across a DLL boundary, and on Android the locale tables `<iostream>` drags in are a measurable binary-size cost. Never on a per-message path |
| `<regex>` | code size and stack depth for no benefit; every predicate here is a character loop |
| `<thread>`, `<condition_variable>` | the core is not concurrent. Its types are **not internally synchronized**, and that is documented rather than fixed: the owner (layer 2, or the consumer) already serializes on its own request thread |
| `dynamic_cast`, `typeid` | RTTI is disabled in some UWP and Android configurations, and is fragile across a shared-library boundary. Use tag dispatch and `static_assert` |
| new exception requirements | see §3.3 |
| platform headers — `windows.h`, `<unistd.h>`, `android/log.h`, `dlfcn.h` | the core is platform-neutral by construction |
| any third-party header — spdlog, rapidjson, Eigen, zenoh | `artekmed` uses spdlog in headers, `tcnart` does not; `tcnart` pimpls Zenoh out of its headers, `artekmed` does not. The core includes **only** the generated `tcnart_msgs` headers and the standard library, and logs nothing (see §4.9) |
| `long double`, assumptions about `sizeof(long)` | MSVC/Android/Linux disagree |
| `memcpy` of a generated struct | they contain `std::string` and `std::vector` |
| a big-endian code path | every target is little-endian and the fixtures are little-endian DDS-CDR. Add a `static_assert` that the build is little-endian, so a future BE port fails loudly instead of producing quiet garbage |
| C++20 conveniences | `std::span`, `starts_with`/`ends_with`, designated initialisers, concepts. Supply two-line internal helpers instead |
| `std::to_chars` for floating point | the FP overloads are missing on the libstdc++ versions shipped with older NDKs. Integral `to_chars` is fine; for FP use `snprintf` with an explicit `"%.17g"` |

### 3.3 Exceptions: the core adds none, and must swallow one

A strictly `-fno-exceptions` build is **already impossible** for anything that
speaks this schema: the generated Fast CDR code throws
`eprosima::fastcdr::BadParamException` and
`eprosima::fastcdr::NotEnoughMemoryException`. So the rule is not "the core
works without exceptions" — it is:

1. **The core throws nothing of its own.** Every failure is a returned value.
   No `throw`, no `.at()`, no `std::get` on a variant alternative.
2. **The core never lets a Fast CDR union exception escape.** A generated
   union's case accessor throws `BadParamException` when the requested member
   is not the current selection — see `include/tcnart_msgs/rpc/SIS.h`, every
   union accessor's `@exception` line. So `reply.handle().topic()` on a `NONE`
   handle **throws**. The core reads a union's discriminator before any case
   accessor, always. `Handle::from_reply` (§4.4) exists precisely to make that
   the only way anyone touches that union.

### 3.4 Symbol visibility and ABI

The core is header-only, so there is nothing to export and no
`eProsima_user_DllExport`-style macro to maintain, no
`WINDOWS_EXPORT_ALL_SYMBOLS`, and no `-fvisibility` agreement to reach with
two consumers who build with different flags. This is not a side benefit of
header-only; it is one of the two reasons to choose it. The other is that the
core's failure modes are compile-time, and a compile-time contract is worth
more inlined into the consumer's TU than behind a link.

## 4. The proposed API surface

Namespace `tcn::sqe` for layer 1, `tcn::sqe::zenoh` for layer 2. Sketches
below are illustrative signatures, not a proposed implementation.

### 4.1 Results, with no exception and no allocation

```cpp
namespace tcn::sqe {

enum class Error {
  Ok = 0,
  Empty, IllegalCharacter, NonAscii, ContainsWildcard, ContainsWhitespace,
  ContainsSlash, EmptyChunk, LeadingSlash, TrailingSlash,
  OriginNotDeclared, HandleAbsent, HandleInvariantViolated,
  ConflictingLease, WrongDeclaredType, MoreThanOneItem,
};

const char* describe(Error);           // static string; no allocation, no locale

template <class T> class Result;       // holds T or Error; no exception, no heap
}
```

`describe` returns a static ASCII string so a consumer can log it through
whichever logger it has. The core never logs.

### 4.2 `ClientId` — a key prefix, validated by the fragment rule

B39 is in here. A client id is a **Zenoh key prefix**, not an identifier: it
contains `/` by design, and validating it with `valid_id` is what panicked the
daemon.

```cpp
class ClientId {
 public:
  // The fragment rule (§4.3): non-empty; every character in
  // [A-Za-z0-9_.:/-]; no empty chunk — so no leading '/', no trailing '/',
  // no "//".
  static Result<ClientId> parse(std::string_view);

  std::string_view str() const;

  // No caller ever concatenates a suffix by hand.
  std::string join_key()          const;  // {id}/sis/join
  std::string leave_key()         const;  // {id}/sis/leave
  std::string alive_key()         const;  // {id}/sis/alive
  std::string node_update_key()   const;  // {id}/sis/component/update
  std::string node_remove_key()   const;  // {id}/sis/component/remove
  std::string edge_update_key()   const;  // {id}/sis/relation/update
  std::string edge_remove_key()   const;  // {id}/sis/relation/remove
  std::string stream_start_key()  const;  // {id}/sis/stream/start
  std::string stream_stop_key()   const;  // {id}/sis/stream/stop

 private:
  ClientId() = default;                   // only `parse` constructs one
};
```

There is no `key(std::string_view suffix)` overload. Nine named accessors is
the point: B1's renames failed silently on the publisher side because nothing
was subscribed to the old key, and a free-form suffix parameter re-opens that.

### 4.3 `NodeName`, `LocalNodeId`, `GlobalNodeId` — two alphabets, kept apart

**The contract here is changing, and this document records the target rule
rather than what the Rust source does today.** `graph::valid_id` currently
tests with Rust's `char::is_alphanumeric`, which is **Unicode-aware** — `é`,
`ü` and `あ` all pass. C++'s `std::isalnum` is ASCII and locale-dependent, so a
naive port disagrees with the engine on any non-ASCII name. Rather than let the
two sides differ — even in the safe direction, where C++ is merely stricter —
**both sides adopt one ASCII rule, and the engine is being changed to match.**
A compatibility entry will record the tightening. Its blast radius in the
engine is nil: there is no non-ASCII identifier anywhere in its sources,
examples or tests, and no test asserts that Unicode alphanumerics are valid.

**The target rule, which is the contract:**

| rule | governs | alphabet | additional structure |
| --- | --- | --- | --- |
| **identifier** (`valid_id`) | node names, edge names | non-empty; every character in `[A-Za-z0-9_.:-]` | — |
| **fragment** (`valid_fragment`) | a client id | non-empty; every character in `[A-Za-z0-9_.:/-]` | no empty chunk — no leading `/`, no trailing `/`, no `//` |

Two things about that shape are the reason for it, and they carry over
verbatim into how it is written in C++:

- **The fragment alphabet is the identifier alphabet plus exactly one
  character, `/`.** That is what makes the two rules one rule with one
  difference, instead of two rules a porter has to keep in sync. It also means
  Zenoh's wildcards (`* ? # $`), whitespace and control characters are
  excluded **structurally, by the allow-list**, rather than by a separate
  blacklist. Today's `valid_fragment` bans the four wildcards with an explicit
  check whose own documentation warns that anyone widening the rule must
  remember to keep them out — **an allow-list cannot be forgotten.** That is
  the argument for expressing it this way in C++ too, and it is why the core
  writes one character-class predicate and derives both rules from it.
- **It is cheap to implement header-only and portably.** No Unicode tables, no
  locale dependence, and specifically **no `<cctype>`** — see §3.2 for why
  `isalnum` is wrong twice over. A plain range check over `unsigned char` is
  correct on every target, and small enough to be `constexpr`.

```cpp
// One predicate, two rules derived from it.
constexpr bool is_identifier_char(unsigned char c);   // [A-Za-z0-9_.:-]
constexpr bool is_fragment_char(unsigned char c) {    // + '/'
  return is_identifier_char(c) || c == '/';
}

class NodeName {                        // the identifier rule
 public:
  static Result<NodeName> parse(std::string_view);
  std::string_view str() const;
};

class LocalNodeId {                     // {fragment}::{name}
 public:
  static LocalNodeId compose(const ClientId&, const NodeName&);
  static Result<LocalNodeId> parse(std::string_view);   // splits at the FIRST "::"
  std::string str() const;
};

class GlobalNodeId {                    // a bare NodeName; nothing about it is a prefix
 public:
  static GlobalNodeId of(const NodeName&);
};
```

Two further notes that are contract, not style:

- `LocalNodeId::parse` splits at the **first** `::`, matching
  `graph::valid_node_id`. `:` is a legal identifier character, so any other
  split is wrong — `a::b::c` is the node `b::c` in fragment `a`.
- **A `GlobalNodeId` is not a key prefix and takes the identifier rule whole.**
  Only a `Local` node's id mixes the two alphabets, and only because its
  fragment half *is* a client id. Keeping `GlobalNodeId` a distinct type is
  what stops someone applying the fragment rule to it "for symmetry" and
  admitting a `/` into a bare global name.

### 4.4 `Handle` — constructible only from a reply

This is B33 and B34 as a type.

```cpp
class Handle {
 public:
  // The ONLY way to obtain one. Reads the union discriminator before any case
  // accessor (§3.3), and enforces the invariant that ASSIGNED occurs exactly
  // when the status is Active or Pending — reporting a violation rather than
  // papering over it.
  static Result<Handle> from_reply(const tcnart_msgs::rpc::SISRelationStreamReply&);

  const std::string& data_topic()   const;   // verbatim from the reply
  std::string        status_topic() const;   // {data_topic}/status

  bool operator==(const Handle&) const;      // lease-table key
};
```

- **There is no constructor taking a string**, no `Handle::compute(observer,
  target)`, and no FNV-1a anywhere in the library. The algorithm *is*
  specified (`engine::relation_handle`, 64-bit FNV-1a over four
  length-prefixed frame fields), and that is not a reason to implement it: an
  implementation is an invitation to B33's exact mistake, and it pins the C++
  side to a hash the engine is free to change. **A specified algorithm is not
  a reason to implement it** — this rule also governs B31's `sqe.derived:`
  name, which uses Rust's `DefaultHasher` and *cannot* be reproduced in C++ at
  all. The core offers `bool is_derived_edge_name(std::string_view)` (a prefix
  match) and nothing that computes one.
- **There is no `descriptor_topic()`.** The engine's own sources disagree on
  whether a client may derive `sqe/{engine_id}/cfg/desc/{handle}`: `SIS.idl`
  says treat all three keys as opaque and read them from the reply, while the
  reply carries only one. The tcnart Phase 2 plan flags this as open (§9). The
  core does not bless a derivation the engine has not blessed. If the engine
  team blesses it or adds the field, this is a two-line addition.
- The stop request accepts a `Handle` and nothing else, so B34's failure —
  sending a topic you chose, which encodes and decodes cleanly and stops
  nothing — does not compile.

### 4.5 `Status` — with the ordinals pinned and the semantics named

```cpp
enum class Status : std::int32_t {
  Active = 0, Inactive = 1, NoPath = 2, UnknownFrame = 3,
  ClockDomainMismatch = 4,   // reserved; the engine never emits it
  Rejected = 5, Pending = 6,
};

// B23's lesson applied to every enum the library mirrors: a renumbering must
// be a compile error, not an unwalkable edge.
static_assert(static_cast<int>(Status::Pending) ==
              static_cast<int>(tcnart_msgs::rpc::SIS_RS_PENDING));
// ... one per enumerator, and the same treatment for SREdgeTemporalType,
// SRNodeScope, SRNodeType, SRTransformType, MarkerType.

constexpr bool is_acceptance(Status s);   // Active | Pending  — do NOT retry
constexpr bool carries_handle(Status s);  // Active | Pending  — the invariant
constexpr bool is_final_for_this_graph(Status s);  // NoPath | UnknownFrame | Rejected
```

`is_acceptance` exists so that "treat `Pending` as acceptance" is a function a
consumer calls rather than a paragraph a consumer reads. The retry loop
against `Pending` is the precise failure the status split was introduced to
end (B13, B35).

### 4.6 `RelationLeaseTable` — the local refcount, and the most likely design error

B36 is the one the engine's own docs single out as *"the single most important
type in the whole API"* on the tcnart side, and *"the most likely design
error"* here. It is worth restating exactly why:

> Requesters are tracked as a **set of client ids**, not a count. Two starts
> from the same client id attach that id **once**, and one stop from it
> detaches **entirely**. A wrapper that expects its own refcounting to nest is
> wrong unless it counts locally.

So two components in one process asking for the same relation get the same
handle, and the first component's stop stops the other one's stream — with no
error anywhere.

```cpp
class RelationLease;                       // move-only, RAII; release == maybe-stop

/// What a start produced: the handle, and the `{handle}/status` subscriber
/// declared for it. Move-only, because `Declaration` is.
struct StreamClaim { Handle handle; Declaration status; };

class RelationLeaseTable {
 public:
  // The integrator supplies these two. The table itself does no I/O -- it
  // stores the `Declaration` and never touches a `Transport` -- which is what
  // makes the arithmetic unit-testable with no daemon (§8).
  using StartFn = std::function<Result<StreamClaim>(const RelationStreamRequest&)>;
  using StopFn  = std::function<Result<Status>(const Handle&)>;

  RelationLeaseTable(StartFn, StopFn);

  Result<RelationLease> acquire(const RelationStreamRequest&);
  // release happens in ~RelationLease

  std::size_t local_count(const Handle&) const;   // for tests and diagnostics
};
```

`StartFn` returns a `Handle` rather than the generated reply so that this
header includes no generated type; `Handle::from_reply` already enforces the
reply invariant on the way through. `StopFn` returns the reply's `Status`,
passed through unread — see below for why the table must not interpret it.

#### The `{handle}/status` subscriber is in the return type, not in the prose

An earlier revision of this design had `StartFn` return a bare `Handle` and
*documented* that the `{handle}/status` subscriber belonged inside it —
declared on the 0 → 1 transition, kept beside the lease, dropped by `StopFn` on
the 1 → 0 transition. Nothing in the type asked for it, so an integrator who
forgot got no error, ever: they simply never learned that a stream they held
went `NoPath`, or that the engine had stopped answering, and those two are not
distinguishable any other way. Per the compatibility record the status publish
is also the **only** teardown event guaranteed to arrive — the pipeline stop,
the descriptor withdrawal and the derived-edge retraction are each gated on the
stream currently holding that thing — so a consumer waiting on a withdrawal
instead just hangs.

So the start returns the `Declaration` too, and the table keeps it:

| rule | prevents |
| --- | --- |
| `StartFn` returns a `StreamClaim`, not a `Handle` | an integrator silently never declaring the one channel that reports `NoPath`, engine loss, or teardown |
| the table stores the `Declaration` in its `Record`, for the record's lifetime | the subscriber's lifetime being the *caller's* instead of the *lease's* — declared per component, N components sharing one stream leave N subscribers on it, and the released ones go on listening to a dead key |
| the `Declaration` is dropped on retire, **after** `StopFn` returns | the engine's final status publish — "retired", or a `NoPath` in the same breath — arriving at a subscriber that has already been undeclared, which is exactly the event a consumer waiting on teardown is waiting for |
| a start whose claim the table does not keep (two spellings converging on one handle) drops its `Declaration` immediately | two subscribers on one stream |

An integrator who genuinely wants no status subscriber returns a
default-constructed `Declaration`. That is deliberate: the type *asks*, it does
not compel, and the returned empty is then a visible choice in the
integrator's own code rather than an omission nobody ever sees.

`Declaration` itself lives in `tcn/sqe/transport.h`, not `tcn/sqe/session.h`.
It is RAII over a `Transport*` and a `Registration`, both defined there, and
its whole job is to call `Transport::undeclare` once; it sat in `session.h`
only because that is where the two factories that produce one are written.
`lease.h` now stores one by value and needs the complete type, and `session.h`
already includes `lease.h`, so the include could not be turned around.

Rules the table enforces, each with the failure it prevents:

| rule | prevents |
| --- | --- |
| a start goes out only when the local count for a handle goes **0 → 1** | a redundant start that the engine answers `Rejected` if the trigger differs |
| a stop goes out only when the local count reaches **0** | one component detaching every other component in the process |
| the table is keyed by the **handle from the reply**, never by the request | two callers spelling the same relation differently and diverging into two records |
| a second `acquire` for an already-leased handle with a **different** `trigger` or `freshness_bias` fails locally with `Error::ConflictingLease`, naming the existing lease's trigger | turning a local misuse into a wire `Rejected` a caller cannot interpret |
| `RelationLease` has **no public `stop()`** | one component detaching the others deliberately. If an escape hatch is ever wanted, name it `force_detach_process_from(handle)` so nobody reaches for it by accident |

And the part the API must **not** claim: a stop always answers `Inactive`, and
that means only *"you are no longer attached."* Another process may still hold
the same handle. `RelationLeaseTable` therefore never reports "stopped" — the
real transition is only visible on `{handle}/status`.

### 4.7 `WireType<T>` — the annotation cannot be forgotten

B2 is universally unmet across both C++ repositories today: `grep -rn
"application/cdr;"` over both returns zero hits. `artekmed` puts the type name
in the Zenoh **attachment**, which the engine never reads, while setting a
bare `application_cdr()`; `tcnart`'s descriptor and marker-pose publishers set
no encoding at all.

```cpp
template <class T> struct WireType;        // no primary definition — unregistered
                                           // types are a compile error

template <> struct WireType<tcnart_msgs::rpc::SISJoinRequest> {
  static constexpr std::string_view name = "tcnart_msgs::rpc::SISJoinRequest";
};
// ... one per registered type, generated from the engine's wire_types! macro.

template <class T> std::string cdr_encoding();   // "application/cdr;<name>"
template <class T> std::string json_encoding();  // "application/json;<name>"

// The parsing counterpart — the C++ decode_typed.
template <class T>
Result<void> check_declared_type(std::string_view zenoh_encoding);
```

Two things this buys that a `cdr_encoding_for(std::string_view)` helper —
which is what tcnart's Phase 1 A2 currently proposes — does not:

- **A caller cannot pass the wrong string**, because it does not pass a string.
  A publish API that takes `const T&` and derives the annotation from `T`
  cannot mismatch payload and annotation, which is B3.
- **An unregistered type does not compile.** `SISJoinMessage` — the name that
  appears in older prose and in B2's own example, and which the engine
  refuses — has no specialization, so it fails at the call site rather than at
  the daemon.

`check_declared_type` matters on the reply path specifically. tcnart's
`comm::Query` round-trips `application/cdr;<type>` as `QueryEncodingKind::other`
with the whole string in `name`, and `is_cdr_like()` returns true for *any*
`other` — so it cannot tell "CDR carrying the type I asked for" from "CDR
carrying something else". That is the `SISJoinMessage`-class bug on the read
side.

### 4.8 Two publication shapes, so one-item-per-message cannot be violated

On a **template** (`"*"`) stream a `Pose6DMapMessage` of many entries is
exactly right: each id is a different discovered marker. On a
**concrete-target** stream it is not — ingest writes *every* item of the
payload into the one buffer the claim names, regardless of the id it arrived
under, so the second item silently overwrites the first with a different
measurement of the same edge.

The core does not document this. It makes them different types:

```cpp
// Takes one pose. Builds the single-entry map itself. There is no overload
// that accepts a map.
class ConcreteTargetPosePublication {
 public:
  static tcnart_msgs::msg::Pose6DMapMessage build(const Header&,
                                                  std::string_view target_id,
                                                  const RigidTransform&);
};

// Takes many. Only legal on a stream whose claim target is "*".
class TemplateTargetPosePublication {
 public:
  static tcnart_msgs::msg::Pose6DMapMessage build(const Header&,
                                                  const std::vector<Instance>&);
};
```

### 4.9 Fragment assembly — the origin precondition, checked locally

A join whose `origin` is not among its own nodes is **refused outright**:
`Engine::on_join` returns no effects at all, the fragment is not created, and
the only trace is a line in the *daemon's* log.

```cpp
class FragmentBuilder {
 public:
  // The origin is a constructor argument, not a field set later.
  explicit FragmentBuilder(const ClientId&, const NodeName& origin);

  Result<void> add_node(const SrNodeSpec&);   // validates the composed id
  Result<void> add_edge(const SrEdgeSpec&);   // both endpoints must be declared

  // Fails with Error::OriginNotDeclared if the origin was never added, and
  // names every edge that would be dropped for referencing a refused node.
  Result<tcnart_msgs::msg::SRGraph> build() const;
};
```

`SrNodeSpec` requires a `CoordinateSystem` with no default. B29's failure mode
is *plausible, wrong poses with nothing in any log*, and a defaulted
convention is how that happens. The core can also refuse a degenerate axis
triple (the same axis named twice), which is cheap and catches a real
copy-paste error; it cannot resolve the open question of how tcnart's
`CoordinateSystem<right, up, forward, handedness>` maps onto the IDL's
`{forward, right, up, dimensions}` — that needs a round-trip test against the
engine, and the Phase 2 plan already flags it.

`FragmentBuilder` returns an `SRGraph`, not a wire message. It does not
publish. Layer 1 does no I/O.

### 4.10 Layer 2 sketch

```cpp
namespace tcn::sqe::zenoh {

// Declared in the constructor, undeclared in the destructor. Nothing is ever
// put on the key — declaring it IS the message (B41).
class Presence { /* RAII over zenoh liveliness_declare_token */ };

class SisSession {
 public:
  // A SisSession cannot be constructed without a Presence. B41 by
  // construction: there is no code path that joins without a token.
  static Result<SisSession> open(::zenoh::Session&, ClientId);

  Result<void> join(const tcnart_msgs::msg::SRGraph&);
  Result<void> leave();
  Result<void> update_node(const tcnart_msgs::msg::SRNode&);
  Result<void> update_edge(const tcnart_msgs::msg::SREdge&);   // incl. calibration

  Result<RelationLease> acquire_relation_stream(const RelationStreamRequest&);
};
}
```

Notes that are contract, not preference:

- **The query timeout must exceed the engine's resolve bound.** The engine's
  `RESOLVE_TIMEOUT` is 30 s. tcnart's `comm::Query` defaults to 5 000 ms and
  blocks on the calling thread. A 5 s timeout gives up on a request the engine
  will still answer — and by then the engine may have registered a stream and
  attached this client id to it, so the consumer holds a stream it has no
  handle for and cannot stop until it leaves.
- **`update_node` / `update_edge` return "published", never "accepted."** That
  is the contract (B27), and the naming should make the return value
  impossible to misread — the tcnart plan's `submit_calibration` spelling is
  right for the same reason.
- **`join` before announcing a descriptor.** Both orders work; announcing
  first leaves a window in which poses are dropped while the coordinate read
  is in flight.

## 5. Packaging: Conan components and CMake targets

### 5.1 Names

| Conan component | CMake target | kind | requires |
| --- | --- | --- | --- |
| `sqe_contract` | `tcn_schema_sqe_contract` | `INTERFACE` (header-only) | `tcnart_msgs` |
| `sqe_transport` | `tcn_schema_sqe_transport` | static/shared, follows `shared` | `sqe_contract`, `zenoh-cpp` |

`sqe_contract` is **not** behind an option. It is header-only, it adds no
library to any link line, and a component with no `libs` costs a consumer
nothing but a header copy — an option here would only create a configuration
in which one consumer has it and the other does not.

`sqe_transport` **is** behind a new option:

```python
options = { "shared": [...], "with_dds": [...], "with_sqe_transport": [True, False] }
default_options = { ..., "with_sqe_transport": False }
```

Default `False` so that no existing consumer of `tcn_schema` — and there are
several that want only ROS 2 messages — inherits `zenoh-cpp` by upgrading.

### 5.2 Where the source lives

**`include/` is not available.** `FASTDDSGEN_OUTPUT_DIR` is
`${PROJECT_SOURCE_DIR}/include` (`src/dds/custom/tcnart_msgs/CMakeLists.txt`),
that directory is the generator's output, and `.gitignore` ignores it
wholesale. Hand-written headers placed there would be untracked and would be
clobbered by a regeneration.

Proposed layout:

```
src/sqe/
  CMakeLists.txt
  include/tcn/sqe/*.h          # the header-only core
  transport/                   # layer 2 sources, guarded by WITH_SQE_TRANSPORT
  fixtures/                    # §6
  test/                        # gtest, guarded by BUILD_TESTING
```

installed as:

```
${CMAKE_INSTALL_INCLUDEDIR}/tcn/sqe/*.h
share/tcn_schema/sqe/fixtures/*
```

The `share/tcn_schema/...` prefix follows the precedent already in the tree:
every module installs its `.idl` to `share/tcn_schema/dds/${module}/...`.

### 5.3 CMake, platform-neutral

```cmake
add_library(tcn_schema_sqe_contract INTERFACE)
target_include_directories(tcn_schema_sqe_contract INTERFACE
  $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
  $<INSTALL_INTERFACE:include>)
target_link_libraries(tcn_schema_sqe_contract INTERFACE tcn_schema_tcnart_msgs)
target_compile_features(tcn_schema_sqe_contract INTERFACE cxx_std_17)
```

Rules for both targets:

- `target_compile_features(... cxx_std_17)`, **never** `set(CMAKE_CXX_STANDARD)`
  — a consumer that has already chosen 17 or 20 must not be overridden. Note
  that `cxx_std_17` requires CMake ≥ 3.8, well under this repo's 3.18 floor
  and both consumers' 3.22.
- No `if(WIN32)`, `if(ANDROID)`, `if(UNIX)` anywhere. There is nothing
  platform-specific to branch on, and the absence of a branch is the
  guarantee.
- No `-Werror`, no hard-coded `-W*` or `/W*` flags. Each consumer sets its own
  warning policy and an `INTERFACE` target must not push flags into it.
- No `find_package` beyond what the module already resolves; no
  `FetchContent`; no network at configure time.
- `WINDOWS_EXPORT_ALL_SYMBOLS` and `POSITION_INDEPENDENT_CODE` apply to
  `sqe_transport` only, matching the existing message targets. The
  `INTERFACE` target has neither because it has no objects.
- `sqe_transport` compiles only when `WITH_SQE_TRANSPORT` is on, and its
  `find_package(zenohcpp)` sits inside that guard so a `with_sqe_transport=False`
  build never needs zenoh-cpp present.
- Everything installs through the same `install(TARGETS ... EXPORT ...)` /
  `install(EXPORT ...)` pattern the existing modules use, so the packaging
  story is uniform.

### 5.4 Two existing defects this design has to work around

Both are pre-existing, both are cheap, and both should be fixed in the same
commit that adds the components — not by this document.

1. **The version has drifted.** `CMakeLists.txt:2` declares
   `project(tcn_schema VERSION 0.2.0 LANGUAGES CXX)` while `conanfile.py`
   declares `version = "0.3.0"`. Conan is authoritative for what consumers
   resolve, so nothing is broken today — but §7 proposes deriving a
   contract-level constant from the project version, and that is not safe
   while the two disagree. Reconcile them, and ideally have one read the
   other.
2. **`tcnart_msgs` carries the wrong legacy find-package name.**
   `conanfile.py` sets
   `self.cpp_info.components["tcnart_msgs"].names["cmake_find_package"] = "device_hl2_msgs"`
   — a copy-paste from the component below it. Every other component names
   itself. This is latent rather than active (the `cmake_find_package`
   generator is legacy), but `sqe_contract` will `requires` `tcnart_msgs`, so
   it is worth correcting before something depends on the wrong name.

## 6. Test vectors and conformance testing

### 6.1 The problem the fixtures already solve, on one side only

The engine hand-encodes CDR fixtures in `tests/wire_fixtures.rs` — 780 lines,
sixteen fixtures — and the file's own header says exactly why they are not
produced by encoding a Rust value:

> that would only prove Rust agrees with itself, which is exactly how
> `src/messages.rs` and the IDL drifted apart unnoticed.

Better still, they are already derived from **the C++ side's** behaviour: the
header records that every artekmed peer serializes through
`pcpd_zenoh::CdrBufferWriter`, which wraps `eprosima::fastcdr::Cdr` configured
for `DDS_CDR` and calls `serialize_encapsulation()` — so every fixture begins
with the 4-byte `00 01 00 00` header and aligns relative to the body. The
fixtures are already a statement about what Fast CDR produces. Nothing on the
C++ side checks them.

B18 item 3 says as much in a sentence: *"when upgrading the C++ side, check
against those rather than against a Rust round-trip."* Nothing does.

### 6.2 Concretely: ship them as data

**Engine side.** Refactor `tests/wire_fixtures.rs` so the byte arrays are
*written to files* by a generator and the existing Rust tests then read those
files. That inversion matters: it makes the files impossible to drift from the
tests, because the tests no longer have their own copy.

```
spatial_query_engine_rs/fixtures/wire/
  manifest.json
  target_tracking_message.cdr
  target_tracking_message.json
  sis_relation_stream_reply_assigned.cdr
  sis_relation_stream_reply_assigned.json
  ...
  identifiers.json
```

- `*.cdr` — the exact bytes, DDS-CDR little-endian with the encapsulation
  header, as the Rust test builds them today.
- `*.json` — the expected decoded field values, plus the expected Zenoh
  encoding annotation for that type.
- `manifest.json` — for each fixture: name, wire type name, encoding string,
  SHA-256 of the `.cdr`, and the B-entries it pins. Plus, once, the engine
  commit it was generated from and the contract B level (§7).
- `identifiers.json` — **predicate vectors**, which the byte fixtures do not
  cover: a list of `{value, valid_id, valid_fragment, valid_publish_topic,
  valid_subscribe_topic}` generated from the Rust predicates. This is what
  catches a `valid_id` / `valid_fragment` divergence, which bytes cannot.

Engine CI regenerates and runs `git diff --exit-code fixtures/`. A change to
`messages.rs` that moves a field fails the diff, loudly, in the repo that
caused it.

**`tcn_schema` side.** Vendor the directory at `src/sqe/fixtures/`, install it
to `share/tcn_schema/sqe/fixtures/`, and add a gtest conformance suite behind
`BUILD_TESTING` that, for every fixture:

1. decodes the `.cdr` with the generated `tcnart_msgs` type and asserts every
   field against the `.json`;
2. **re-encodes and asserts the bytes are identical** — this is the check that
   catches a field-order or padding drift, and it is meaningful precisely
   because the fixtures were derived from Fast CDR's own alignment behaviour
   (§6.1);
3. asserts `tcn::sqe::cdr_encoding<T>()` equals the manifest's `encoding`
   string, byte for byte, with no space after the `;`;
4. for `identifiers.json`, asserts each predicate agrees **exactly**. Because
   both sides now implement the same ASCII allow-list (§4.3), there is no
   tolerated asymmetry to encode: a disagreement on any vector is a failure.
   The generated vector list must include the characters the allow-list
   excludes structurally — each Zenoh wildcard, a space, a tab, a control
   character, a non-ASCII byte sequence — precisely because nothing in either
   implementation names them any more, so only a vector proves they are out.

**Negative fixtures matter as much as positive ones.** The engine already has
`a_pre_handle_start_request_does_not_quietly_decode_as_the_new_one` — B32's
removed `output_topic` sat third, and an un-rebuilt encoder does not fail, it
*misreads*. That fixture must ship and the C++ suite must assert the decode
**fails**.

### 6.3 Drift detection

The vendored manifest records the engine commit. `tcn_schema` CI fails if the
vendored `manifest.json` differs from the engine's at the recorded commit.
Engine CI fails if regeneration produces a diff. So a wire change is caught in
CI in the repo that made it, and a stale vendor is caught in CI here —
neither is discovered in a lab.

Cost, stated: this is a real piece of cross-repo CI plumbing, and `tcn_schema`
has **no test infrastructure at all today** (§10.2). It is the largest single
piece of new work in this proposal that is not the library itself.

## 7. Versioning: the contract and the IDL change together

This is the argument for `tcn_schema` as the home, and it is worth stating as
evidence rather than as preference. Look at what the recent breaks actually
did:

| break | IDL change | contract change |
| --- | --- | --- |
| B32 | removed `output_topic` from `SISRelationStreamStartRequest` | the client no longer chooses the topic |
| B33 | reply becomes struct + union instead of a bare enum | take the handle from the reply; handle the `NONE` case |
| B34 | field renamed, **wire layout unchanged** | the *value* must be the engine-issued handle |
| B23 | `SREdgeTemporalType` ordinal 1 changed meaning | a 0.2.0 "static" edge is now unwalkable |
| B5 | two fields appended to `StreamDescriptorMessage` | C++→Rust hits EOF without a rebuild |

In every one of these the C++ *type* and the C++ *rule* moved in the same
release. If they live in separate packages, a consumer can resolve a version
pair that never existed and that nobody tested — 0.3.0 types with a
contract library that predates B34, say, which compiles fine and stops
nothing. In one package there is one coordinate to pin and the pair cannot be
invalid.

B34 is the sharpest case: the wire layout did **not** change, so the rename is
the *only* signal a peer gets, and it is only a signal if the header and the
rule ship together.

**And the identifier tightening of §4.3 is the opposite case, which is worth
being straight about: it changes the contract and changes no IDL at all.**
B30's opening line is *"no IDL field describes any of this"*, and it is right —
`SRNode.name`, `SREdge.name`, `SREdge.source`/`target` and `SISFrameRef.node`
are all bare `string` on the wire. So that change cannot ride the IDL, and a
release note is the only thing that carries it. That does not undercut §7's
argument; it sharpens what the library is *for*. The types are the half the
IDL already expresses. The rules are the half it cannot, and today they exist
only as prose in another repository that neither consumer builds against.
`kContractBLevel` is what makes such a change detectable at compile time
instead of at a daemon nobody is watching.

**Proposal.**

- `sqe_contract` is versioned by `tcn_schema`'s version and released only with
  it. There is no independent release.
- The header exposes the highest compatibility-break entry it implements:

  ```cpp
  namespace tcn::sqe {
  inline constexpr int kContractBLevel = 42;   // highest B-entry implemented
  }
  #define TCN_SQE_CONTRACT_B_LEVEL 42
  ```

  so a consumer can write `static_assert(tcn::sqe::kContractBLevel >= 41)`
  next to the code that depends on the liveliness token, and get a compile
  error rather than a swept client.
- The fixture manifest carries the same B level. The conformance suite fails
  if the fixtures' level is *below* the header's — that combination means the
  library claims to implement a break the vendored vectors do not cover.
- Any wire-visible change bumps the minor version, and the `kContractBLevel`
  bump lands in the **same commit** as the IDL change. A commit that changes
  an `.idl` under `tcnart_msgs/{msg,rpc}` and does not touch either
  `kContractBLevel` or the fixtures is a reviewable smell.

## 8. What becomes testable, and where

The tcnart Phase 2 plan has a table of "what can be verified without a running
engine". Nine of its eleven rows are pure contract-core properties and move
into `tcn_schema`, where they are written and run **once** instead of twice:

| Phase 2 §8 row | lands as |
| --- | --- |
| the client id satisfies `valid_fragment` | `ClientId::parse` tests + `identifiers.json` |
| every id satisfies the identifier rule | `NodeName::parse` tests + `identifiers.json` |
| `origin` is among the declared nodes | `FragmentBuilder::build` returns `OriginNotDeclared` |
| `temporal_type` ordinals pinned | the `static_assert` table of §4.5 |
| the union filler byte | a fixture: encode `OnAny`, assert 5 bytes not 4 |
| the encoding annotation for all eleven type names | table-driven over `cdr_encoding<T>()`, cross-checked against the manifest |
| **the lease table's arithmetic** | `RelationLeaseTable` with fake `StartFn`/`StopFn`: acquire twice, release once, assert **no** stop; release again, assert exactly one stop carrying the reply's handle |
| **the status subscriber's lifetime** | the same fixture over a `FakeTransport`: the `Declaration` the start returned is held after a non-final release, still held *while* `StopFn` runs, and undeclared only after it returns |
| status seeding | feed a `Pending` reply, assert the lease reports `Pending`, not `Inactive` |

The two rows that stay in tcnart are the ones about tcnart's own comm layer:
the `zenoh::Encoding` round-trip of the `;schema` string, and `comm::Query`'s

Everything about adoption, path resolution, `Pending → Active` on a
calibration push, and cross-process shared-handle behaviour still needs a live
daemon. Note the asymmetry both plans already record: **the engine logs, and
neither C++ repo does.** For every silent obligation, the daemon's stdout is
the only signal.

## 10. Costs, risks, and what argues against this

### 10.1 The strongest argument against — the two consumers are on different zenoh-cpp versions

`tcnart` pins `zenoh-cpp/1.3.4@camposs/stable` (`conanfile.py:123`).
`artekmed` pins `zenoh-cpp/1.9.0@camposs/stable`
(`libs/pcpd_dependencies/conanfile.py:109`).

A shared `sqe_transport` component must either force a common zenoh-cpp on
both — a dependency bump neither has scheduled, in a diamond with everything
else each repo links — or abstract over the parts that differ, which is
building a second Zenoh wrapper on top of the two each repo already has.

It gets worse when you look at what layer 2 would actually contain once layer
1 has taken the lease table (§4.6) and the type traits (§4.7). What is left
is: an RAII token, a `get` with a type check and a longer timeout, and two
subscriber declarations. **Each consumer already has wrappers for exactly
those**, and their idioms differ in ways the shared version would have to
straddle:

| | `tcnart` | `artekmed` |
| --- | --- | --- |
| zenoh in public headers | **no** — pimpl throughout (`comm/publisher.hpp`) | **yes** — `zenoh::Session::PutOptions` used directly at call sites |
| result type | `tcnart_result_t` | `pcpd::datatypes::pcpd_result_t` |
| logging | its own | `spdlog`, included from headers |
| CDR codec entry point | `serialization/cdr_serialization.h` | `pcpd::serialization::CdrBufferWriter` / `CdrBufferReader` |

**Recommendation.** Ship `sqe_contract` first and standalone. Treat
`sqe_transport` as a design held open — specified here, built only if, after
both consumers have integrated the core, a second consumer still wants it.
The zenoh version question then either resolves itself (the pins converge) or
stays a reason not to build it. This costs nothing: layer 1 is useful without
layer 2, and layer 2 was always going to be the smaller half.

### 10.2 `tcn_schema` is not currently a C++ repository

It is 153 tracked files of `.idl`, `CMakeLists.txt` and `conanfile.py`. There
is **no hand-written C++ source, no test target, no `docs/` directory** (this
file creates one), and `include/` — the obvious home for headers — is the
generator's output directory and is gitignored.

Adding a hand-written library changes what this repository is, and requires
infrastructure that does not exist: a gtest dependency (test-only, behind
`BUILD_TESTING`, so consumers do not inherit it), a `test_package`, and CI
that compiles C++ rather than just running a generator. §6's cross-repo
fixture check sits on top of that. This is the second-largest cost after the
library itself, and it is easy to underestimate because the *library* is
small.

Mitigation: `sqe_contract` being header-only keeps the build story minimal —
there is nothing to compile in the package itself, only in the test target.

### 10.3 Release coordination, and the burden if they cannot move in lockstep

They demonstrably do not move in lockstep. Today: `artekmed` on 0.1.1,
`tcnart` on 0.2.0, the engine reading 0.3.0. A contract fix now requires a
`tcn_schema` release, which forces any consumer taking it to also take *every*
IDL change since its own pin.

For `artekmed` that is 0.1.1 → 0.3.0+, which includes the entire SIS/SRG
redesign (B9), the `PoseTracking` changes, and the `StreamDescriptor` append.
It is a real port, and a contract fix cannot be delivered to `artekmed`
without it.

Honest assessment: **this is not made worse by the shared library.** Those
changes are already required for `artekmed` to speak to the engine at all
(B18 items 1 and 5). What the library adds is that a *contract-only* fix — one
that would otherwise be a two-line change in each repo — now also rides a
schema release. Mitigations:

- the core is header-only and additive, so taking a newer one is a recompile,
  not a link change;
- `kContractBLevel` (§7) lets a consumer detect an old library at compile time
  rather than at runtime;
- a consumer that cannot move may pin an older `tcn_schema` and simply not get
  the fix — which is exactly today's situation, no worse.

### 10.4 The library bakes in the engine's rules, and the engine may change them

The identifier rules are the sharpest instance, and the decision in §4.3
removes most of the risk rather than managing it: both sides implement one
ASCII allow-list, so there is no standing divergence to reason about, and the
allow-list shape means a future widening cannot silently readmit a wildcard.

What remains is the general case. If the engine changes any predicate, a
consumer on an older `sqe_contract` diverges in one of two directions:

- **refusing a name the engine would now accept** — a false negative. Safe: a
  local refusal with a message beats a silent remote drop, and the predicate
  vectors in §6.2 catch it at build time as soon as the vendored fixtures are
  updated;
- **accepting a name the engine would now refuse** — a false positive, and the
  bad direction, because the failure is the silent kind again. The vectors
  catch this only if the engine's generated list includes the
  newly-refused input.

So the residual risk is asymmetric, and the mitigation is procedural: **when a
predicate is tightened, add the newly-refused inputs to the vector list in the
same commit.** That is a review rule, not a mechanism, and it is worth stating
as a known soft spot rather than claiming §6 closes it.

### 10.5 Two more things the core deliberately will not do

Both are cases where a specification exists and implementing it would be
wrong:

- **The FNV-1a handle.** Specified in `engine::relation_handle`, and
  implementing it is B33's exact mistake. Get it wrong and you subscribe to a
  topic nothing publishes on; get it *right* and you are pinned to a hash the
  engine is free to change.
- **The derived-edge name.** B31 is explicit that it uses Rust's
  `DefaultHasher` — SipHash with a fixed unkeyed seed, deterministic for a
  given Rust toolchain and *not* portable. A C++ implementation **cannot**
  produce the same name. The core offers a prefix predicate and nothing more.

A consumer that wants either of these has, so far, always been about to make a
mistake. Refusing to provide them is a feature, but it is a feature that will
be argued about, so it is written down here.

### 10.6 Alternatives considered

| alternative | why not |
| --- | --- |
| **A separate `tcn_sqe_client` Conan package** | decouples release cadence, which sounds attractive until §7: the contract and the IDL move together, and a separate package lets a consumer resolve a version pair that never existed. It also adds a diamond — both consumers would pin `tcn_schema` *and* `tcn_sqe_client`, which pins `tcn_schema` |
| **Generate the C++ client from the engine's Rust via cbindgen** | single source of truth, and genuinely the most drift-proof answer. But it means a Rust toolchain in the build for Android, WindowsStore, Jetson and MSVC, cross-compiled for five targets, in two repositories that have no Rust today. Not proportionate |
| **Do it twice, carefully, with the engine docs as the checklist** | the status quo, and the honest baseline. It is not absurd — the engine's `integrating-a-client.md` is a good checklist. It fails on the same ground as everything else here: every rule on that checklist fails *silently*, so "carefully" is unverifiable, and it is already known not to have worked (B18 item 4: zero `application/cdr;` annotations across both repositories) |
| **Put the shared code in `tcnart` and have `artekmed` depend on it** | `artekmed` would inherit OpenCV, ffmpeg, aruco, taskflow and the rest of tcnart's dependency graph for a header of string functions |

## 11. Summary of what is proposed

1. Add two Conan components to `tcn_schema`: **`sqe_contract`** (header-only,
   `INTERFACE`, no option, no new dependency) and **`sqe_transport`**
   (compiled, behind `with_sqe_transport`, default off, requires zenoh-cpp).
2. Build and release **`sqe_contract` first and standalone.** Hold
   `sqe_transport` open until the zenoh-cpp version question resolves (§10.1).
3. Adopt one **ASCII allow-list** for identifiers and fragments on both sides
   (§4.3) — identifier `[A-Za-z0-9_.:-]`, fragment the same plus `/` with no
   empty chunk — so the wildcards, whitespace and control characters are
   excluded structurally rather than by a blacklist that can be forgotten. The
   engine is being tightened to match; a compatibility entry records it.
4. The core expresses every silent rule as a type: `ClientId`, `NodeName`,
   `LocalNodeId`, `Handle` (constructible only from a reply), `Status` with
   pinned ordinals and named semantics, `RelationLeaseTable` with local
   refcounting, `WireType<T>` with no primary definition, two distinct pose
   publication shapes, and a `FragmentBuilder` that takes the origin as a
   constructor argument.
5. Written to C++17 under the explicit platform rules of §3 — no
   `<filesystem>`, no `<cctype>`, no locale-dependent formatting, no RTTI, no
   new exception requirement, no platform header, no third-party header.
6. Ship the engine's `wire_fixtures.rs` byte vectors and its identifier
   predicates as **data**, vendored here, verified by a gtest conformance
   suite, with drift caught by CI in both repositories.
7. Version the contract with the IDL, expose `kContractBLevel`, and require
   the IDL commit and the contract commit to be the same commit.
8. Fix the two pre-existing packaging defects in §5.4 while doing so.
