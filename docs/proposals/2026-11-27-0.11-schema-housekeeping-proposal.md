# Proposal: tcn_schema 0.11 — housekeeping (encoding, ROS 2, deletions, structure)

2026-11-27. Status: **decided**: see [0.11-decisions.md](0.11-decisions.md), which wins where the two differ. This is documentation only, with no IDL change.

**Scope:** the repository as a whole. The four team proposals cover what the types *say*:
- SQE: #35
- conversation_msgs: #36
- tcnart: #37
- HTA: #38

This proposal covers four questions:
- **What the repository contains:** which files and types go (§4).
- **How everything is encoded on the wire:** XCDR2, as agreed in #35 D1 (§2).
- **How the ROS 2 copies are kept**, with robot integration as a planned extension (§3).
- **How the repository is laid out and built** (§5).

§6 lists, per team, what changes and what to check. Item ids (`E…` encoding, `R…` ROS 2, `X…` deletions, `O…`
organisation) are for the review discussion.

Two companion appendices let you check the items against your own code:
- `2026-11-27-0.11-type-usage-appendix.md` lists every one of the 449 top-level types, with its verdict and one
  code location per consumer.
- `2026-11-27-0.11-field-usage-appendix.md` lists every field of a kept struct that no producer writes, with its
  producer and reader locations.

## 0. Summary

- **Who counts.** The consumers that count are tcnart, the SQE engine, HTA, the tcn web controller and IVA. artekmed is
  deprecated (replaced by HTA), so a type used only by artekmed is not kept for it.
- **E. XCDR2 works with the toolchain we have.** It was tested on fast-dds-gen 3.0.0 and fast-cdr 2.0.0; no upgrade
  is needed.
  - The change is a runtime setting on the encoding side: writers use `XCDRv2` and `DELIMIT_CDR2`. The encapsulation
    id then goes from `00 01` to `00 09`.
  - The web controller has already implemented XCDR2 in TypeScript.
  - Three pitfalls need explicit rules (§2.3).
  - **ROS 2 types stay XCDR1** (`@final`, `00 01`), so they remain byte-compatible with ROS 2.
- **R. Prepare the ROS 2 copies for robot integration in 0.11, so that it needs no further break.**
  - No code sends or receives ROS 2 messages today. Integrating ROS 2 robots is a future extension, and that is why
    the schema side is done now:
    - with no ROS user, the refresh costs nothing today;
    - later, every ROS-side change would be a wire break for whoever uses the types by then.
  - In 0.11:
    - regenerate the copies by script from one distro, Jazzy Jalisco, the LTS for Ubuntu 24.04, which is our main
      release;
    - mark them `@final` (XCDR1, byte-compatible with ROS 2);
    - complete service and action types;
    - ROS type names and RIHS01 type hashes for rmw_zenoh, in a generated table;
    - package tiers for the typical robot interfaces;
    - upstream file names.
  - On the wire, the refresh changes only `sensor_msgs/Range`, which gains a `variance` field. Nobody uses it.
  - Only the zenoh adapter comes later (keys, attachment, discovery tokens). It lives in a transport library and needs
    no schema change.
- **X. Delete in three groups:**
  - **Group A**, no use anywhere:
    - one IDL file: `tcnart_msgs/rpc/SpatialRelations.idl`;
    - two more files, `Logging` and `pcpd_msgs/Instance`, once artekmed's use is discounted;
    - unused structs in `Types.idl`, pcpd_msgs and the parameter RPC.
  - **Group B**, used only by tcnart's legacy v2 code: 13 files, including the HoloLens 2 and Orbbec packages. v2 is
    deprecated and does not count as a consumer, so this group is deleted in 0.11 too.
  - **Group C**, added in 0.10.5 but not yet used: two files, TimeRef and HumanPose. They need their owners'
    decision.
  - The number of custom files drops from 43 to 27 (25 if group C goes as well).
- **F. Fields nobody writes are removed** (decided rule; §4.5).
  - About 50 fields of kept structs are never set, or set only to a constant. Examples: `target_origin`, `quality`,
    `Target.markers`, `SRNode.node_template`, and most `TtsRequest` options.
  - The projects that still read them get a fix list (§6).
  - The scan also found two engine bugs: names and descriptions are dropped, and `is_tracked` is ignored. The SQE
    fixes both in engine B98, still on 0.10.x.
- **O. Reorganise along the lines #35 already breaks:**
  - an `sqe_msgs` package for the SQE protocol;
  - a small `tcn_types` package for the shared structs that #35, #37 and #38 each propose;
  - `SIS.idl` and `Types.idl` split by topic;
  - unique file names, which fixes the shipped-header collision;
  - code generated outside the source tree;
  - generated enum and type tables for every consumer;
  - a round-trip test for every type.

  `tcnart_msgs`, `pcpd_msgs` and `conversation_msgs` keep their names.

## 2. Encoding: XCDR2 for tcn types, XCDR1 for ROS 2 types

#35 D1 asks for XCDR2 with `@appendable`. All four teams said yes, and the web controller has implemented XCDR2 in
TypeScript. This section records what the toolchain does, so the decision can be made with the details known.

### 2.1 What was tested (fast-dds-gen 3.0.0, fast-cdr 2.0.0, as pinned in `conanfile.py`)

- **The generator does not decide XCDR1 vs XCDR2.**
  - fast-dds-gen 3.0.0 has no `-cdr v1|v2` option.
  - Each generated type branches at runtime on `get_cdr_version()`:
    - `@final` gives PLAIN_CDR2;
    - `@appendable` gives DELIMIT_CDR2;
    - `@mutable` gives PL_CDR2.
  - Under `DDS_CDR`, all of them fall back to plain XCDR1.
- **Default extensibility.**
  - The default is `-de appendable`, so every type we generate today is already "appendable" in the generated code.
    That has no effect on the wire, because every peer writes with `CdrVersion::DDS_CDR`.
  - **Today's wire is plain XCDR1 with encapsulation `00 01`.**
  - Our pinned 3.0.0 generated the ROS 2 `std_msgs::msg::Header` as appendable as well, even with `-typeros2`.
    The fast-dds-gen 4.3.1 source makes `-typeros2` imply FINAL, but 3.0.0 does not behave that way.
- **Round trips (Release fast-cdr 2.0.0), all passing:**
  - appendable V2 → V1 (extra trailing field skipped);
  - V1 → V2 (new field absent);
  - `@optional` present and absent;
  - a union switched on an enum;
  - a `@final` struct nested in an appendable one;
  - sequences.

  Example, appendable `{a=7, b="hi", @optional c=1.5, d=…}`:
  ```
  00 09 00 00 | 1c 00 00 00 | 07 00 00 00 | 03 00 00 00 68 69 00 | 01 | 00 00 00 00 00 00 f8 3f | 88 77 …
  encap D_CDR2 LE | DHEADER=28 | a | b | presence | c (8-byte values aligned to 4 in XCDR2) | d
  ```
- **`@optional` is broken under today's `DDS_CDR`.** A V2 with `c` set decodes with `c` absent and `d` garbage, and
  no error is raised. This confirms the warning in MIGRATION-0.9.0, and it means L2 in #36 and P3 in #35 need XCDR2.
- **XCDR1 with `@optional`** (PID headers) round-trips, but it adds no DHEADER. It therefore gives no tolerance for
  appended fields and does not meet #35's P5.

### 2.2 Proposal

- **E1. tcn types use XCDR2.**
  - This covers every type in `tcn_types`, `sqe_msgs`, `tcnart_msgs`, `pcpd_msgs` and `conversation_msgs`.
  - Every struct is declared `@appendable` in the IDL, explicitly, not only through the generator default.
  - Writers construct `Cdr(…, XCDRv2)`, call `set_encoding_flag(DELIMIT_CDR2)`, then `serialize_encapsulation()`.
  - The encapsulation is `00 09` (D_CDR2, LE).
- **E2. ROS 2 types stay plain XCDR1.**
  - Every type under `src/dds/ros2/` is annotated `@final` **in the IDL file**.
  - A top-level ROS 2 message is written with `DDS_CDR` and `00 01`, exactly as rmw_zenoh and rmw_fastrtps write it
    (§3.3).
  - No ROS 2 peer exists today. But `sensor_msgs/PointCloud2` and the other copies are already on our wire (HTA,
    tcnart and the web controller send PointCloud2 between themselves). Making them appendable now would force a
    second break when robot integration starts.
  - **Why in the IDL file and not with `-de final`:** fastddsgen regenerates included IDL inside each package's run.
    `std_msgs/Header` included from `tcnart_msgs` would then follow the `tcnart_msgs` run's flags.
  - A ROS type nested inside a tcn type, such as `std_msgs/Header` as the first member of a stream message, is
    encoded with the outer type's XCDR2 rules. Being `@final`, it has no DHEADER of its own.
- **E3. The encoding belongs to the package, not the topic.**
  - The `application/cdr;{TYPE};tcn_schema=0.11` annotation (#35 V1) names the type, so a reader knows which rule
    applies.
  - The encapsulation id alone also tells it, because readers switch on `read_encapsulation()`.
  - For example, HTA's `PointCloud2` stays `00 01`, and its zero-copy prefix is unchanged.
- **E4. conversation_msgs gets the encapsulation header.**
  - Today it travels as plain CDR without one (MIGRATION-0.10.2).
  - Headerless XCDR2 trips an assertion in Debug fast-cdr (`Cdr.cpp:3087`), because `set_encoding_flag` without
    `serialize_encapsulation()` leaves the internal state inconsistent. Release builds emit correct bytes.
  - Adding the header resolves this, and it is also #37 T16. IVA's own codec (`crates/tcn-wire`) changes anyway.
- **E5. Decode rule: decode into a fresh object.**
  - When a shorter payload is decoded into an object that is being reused, fast-cdr leaves the missing trailing
    members untouched (verified). Generated host codecs (C#, TS, Rust) should reset them as well.
- **E6. Unknown enum values decode and report as `…_UNKNOWN`** (#38 on D1).
  - Every tcn enum gets an explicit first enumerator `…_UNKNOWN` or `…_NONE`.
  - This needs one renumbering pass in 0.11: about 30 kept enums start with a meaningful value at 0. Examples:
    `VideoPixelFormat` (`PixelFormat_NV12`), `SISMutationStatus` (`SIS_MU_ACCEPTED`), `SRStreamTriggerKind`, and
    conversation_msgs' `InteractionMode`.
  - **Unions too** (gap reported by the web controller): every union is `@appendable` and switches on an enum with
    `…_UNKNOWN`. A reader that meets a case it does not know skips the case body by its DHEADER and decodes the union
    as `…_UNKNOWN` with no member.
    - Without this rule a new union case would stay a lockstep change, even under XCDR2.
    - The web controller has implemented E6 for enums. The union part is new.
  - This rule is **normative** for every codec. It is what makes new enumerators and union cases additive in 0.11.x
    (§7, scope rule).

- **E7. Small leaf structs are `@final`:** `Vector2`, `Vector3`, `Quaternion`, `RigidTransform`, `SRPoint2D`, and
  (through E2) `builtin_interfaces/Time`. The web controller proposed this in its #35 review.
  - These will never gain a member, and each appendable instance would cost a 4-byte DHEADER in the high-rate streams
    (`TargetTrackingMessage.targets`, relation outputs).
  - It has to be decided in 0.11: switching a type between final and appendable later is itself a wire break.
- **E8. Evolution rule.** An appendable reader fills the trailing members that a shorter payload lacks with defaults:
  0, `""`, an empty sequence, the **first** enumerator, the first union case, an absent `@optional`.
  - So from 0.12 on, a new member is `@optional`, unless 0, `""` or empty is a true reading of it.
  - With E6, a missing enum member then reads as `…_UNKNOWN`.
- **E9.** Encapsulation ids are the XTypes 1.3 / fast-cdr 2 ones only: `00 06`/`00 07` CDR2, `00 08`/`00 09`
  D_CDR2, `00 0a`/`00 0b` PL_CDR2. Not XTypes 1.2's `0x0010`–`0x0015`. `@mutable` (PL_CDR2) is not used.

### 2.3 Pitfalls each codec must handle

| Pitfall | Applies to |
|---|---|
| A DHEADER (uint32 byte length) before every appendable struct **or union**. A `@final` union has none: fast-cdr's `begin_serialize_type(PLAIN_CDR2)` writes nothing. Unions declare their extensibility explicitly in the IDL, like structs (E1). | every non-fastcdr codec |
| A DHEADER before every **sequence or array whose element type is not primitive**: structs (including `@final` ones), strings, unions, nested sequences. Sequences of numbers, booleans and enums get none. (Reported by the web controller from its byte-for-byte comparison with fast-cdr 2.0.0.) | every non-fastcdr codec |
| 8-byte members (double, int64) aligned to **4** under XCDR2, not 8 | every non-fastcdr codec |
| A one-byte presence flag before each `@optional` member | every non-fastcdr codec |
| A nested `@final` struct has no DHEADER | every non-fastcdr codec |
| The encapsulation id is set by the writer: `Cdr(…, XCDRv2)` without `set_encoding_flag(DELIMIT_CDR2)` writes `00 07` followed by DHEADERs, which a strict decoder misparses | every C++ writer (tcnart, HTA, sqe_client_cpp) |
| A zero-copy writer computes the payload offset: XCDR2 adds DHEADERs to the prefix | tcnart video and time-ref encoders, HTA `VideoStreamMessage` |

Golden files: the engine's `fixtures/wire` gets XCDR2 golden files, cross-checked with fast-cdr. They include an
evolution pair: an appended member read with the older type, and the reverse. They are shared with tcn_schema's
`test/golden/` (O8). The web controller has offered its fast-cdr generator and tests for this.

Codecs that have to change:
- the SQE engine's Rust codec;
- the web controller's TS codec (done, branch `cdr-xcdr2`);
- tcnart's Unity C# codec (`TcnartCdr`/idlgen) and its two zero-copy encoders;
- IVA's Rust `tcn-wire`;
- HTA's hand-written serde and Python helpers.

fast-cdr users only change how they construct the encoder. An optional upgrade to fast-cdr 2.3.x (on conancenter,
still API-compatible with gen 3.0.0) would bring later fixes; it is not tested here.

### 3.3 Talking to ROS 2 robots: what it takes

There are two ways for a zenoh peer to exchange messages with ROS 2 nodes.

**(a) Directly with rmw_zenoh.**
- rmw_zenoh is ROS 2's zenoh middleware, Tier 1 in Kilted per REP-2000. The Lyrical tier was not verified. It has
  branches for humble, jazzy, kilted, lyrical and rolling.
- Its own README says other zenoh applications may interoperate if they follow its design for keys, serialization,
  attachments and liveliness tokens. The requirements (rmw_zenoh `docs/design.md`):
  - **Payload.** XCDR1 `DDS_CDR`, with the 4-byte encapsulation `00 01 00 00` on LE. **This is what we already
    write.**
  - **Key.** `<domain_id>/<topic without leading/trailing '/'>/<dds type name>/<type hash>`, for example
    `0/robot1/chatter/std_msgs::msg::dds_::String_/RIHS01_df668c74…1a18`. Services use the service type
    (`example_interfaces::srv::dds_::AddTwoInts_`).
  - **Type hash.** `RIHS01_` followed by the SHA-256 of rosidl's JSON type description:
    - The description covers field names, types, bounds and every nested type. Comments and defaults are excluded.
    - A service hash also covers the generated `_Event` type, and through it `service_msgs/ServiceEventInfo`.
    - It is **specific to a distro**: a Humble node puts `TypeHashNotSupported` in its key and cannot talk to Jazzy or
      later.
  - **Attachment, mandatory.** 33 bytes: an int64 sequence number, an int64 source timestamp in ns, a length byte
    (16), and a 16-byte GID. Subscribers drop samples without it.
  - **Liveliness tokens** `@ros2_lv/<domain>/<zid>/<node>/<entity>/<MP|MS|SS|SC>/…/<type>/<hash>/<qos>`. A peer needs
    them so that `ros2 topic list` and `wait_for_service` see it.
  - **QoS.** TRANSIENT_LOCAL topics (`/tf_static`, `/map`) need zenoh-ext AdvancedPublisher/AdvancedSubscriber with
    history.

**(b) Through zenoh-bridge-ros2dds,** one bridge per DDS robot.
- Keys are the plain topic names (no type and no hash), and payloads are raw CDR.
- It is simpler to speak, but it cannot interoperate with rmw_zenoh, and robots from Kilted on increasingly run
  rmw_zenoh natively.

**Conclusion.** Our payloads are already right. What tcn_schema lacks for direct interop:
- the type names and hashes per distro;
- the complete service and action types;
- a defined set of packages.

The zenoh adapter itself (keys, attachment, liveliness) belongs in a transport library, not in the schema. It is a
later, additive project.

### 3.4 Proposal

No code sends or receives ROS 2 messages today; integrating ROS 2 robots is a planned extension. **The goal is that
the integration needs no further schema break,** so 0.11 does all of the schema side: R1–R6 and E2.
- This is the cheapest moment: nothing uses ROS 2 messages yet.
- Every change made later is a wire break for whoever uses the types by then. That covers the content refresh, the
  extensibility, the file names, and the derived service and action types.
- Only the zenoh adapter comes later. It needs no schema change.

- **R1. Target distro: Jazzy Jalisco** (decided).
  - Jazzy is the ROS 2 LTS for Ubuntu 24.04, which is our main release, and it is supported until May 2029. Lyrical
    (May 2026) targets Ubuntu 26.04.
  - Against our copy, Jazzy changes only the `Range` field on the wire, plus the `NavSatStatus` constants and default
    (§3.2). `Range` has no user (appendix: generated only).
  - `Pose2D` is still part of Jazzy and stays.
  - rmw_zenoh has a jazzy branch with binaries, but is not Tier 1 there per REP-2000 (Tier 1 from Kilted on). That
    matters for the later adapter, not for the schema.
- **R2. Generate the ROS 2 tree with a script; never edit it by hand.**
  - The script is `tools/ros2/refresh.py`:
    1. clone the upstream repositories at the distro tag (pinned commits recorded in
       `src/dds/ros2/UPSTREAM.lock`);
    2. convert `.msg`/`.srv`/`.action` to IDL with `rosidl_adapter`, which is pure Python and needs only empy;
    3. synthesise the derived service and action types with `rosidl_parser`: `_Request`/`_Response`/`_Event`,
       `_SendGoal_*`, `_GetResult_*`, `_FeedbackMessage`;
    4. add `@final` (E2);
    5. compute the RIHS01 hashes with `rosidl_generator_type_description` (pure Python; packages are processed in
       dependency order);
    6. write `share/tcn_schema/ros2_types.json` (R3).
  - The hashes are checked against known values, for example the `std_msgs/String` hash from rmw_zenoh's design
    document.
  - The script runs offline in CI and fails when the output differs from what is committed.
- **R3. A generated ROS type table:** `ros2_types.json`, plus a C++ header from the same data. Per type it gives:
  - the ROS name (`sensor_msgs/msg/PointCloud2`);
  - the DDS name (`sensor_msgs::msg::dds_::PointCloud2_`);
  - the RIHS01 hash for the target distro;
  - the generated C++ type;
  - the kind (msg, srv, or action and its parts).

  This is what any future adapter, and the web controller or SQE when showing ROS topics, read instead of
  hard-coding strings.
- **R4. Package tiers.** Selected by a CMake option `TCN_SCHEMA_ROS2_TIERS` and a matching conan option. Default:
  `core`.

  | Tier | Packages | Built by default |
  |---|---|---|
  | `base` (always) | builtin_interfaces, std_msgs, geometry_msgs, sensor_msgs | yes: tcn types, tcnart v3 and HTA need them |
  | `core` | + nav_msgs, trajectory_msgs, diagnostic_msgs, visualization_msgs, shape_msgs, std_srvs, stereo_msgs, unique_identifier_msgs, action_msgs, service_msgs, rcl_interfaces, lifecycle_msgs, rosgraph_msgs, statistics_msgs, tf2_msgs, type_description_interfaces | yes (all in ROS 2 `ros_core`/`ros_base`) |
  | `manipulation` | control_msgs, controller_manager_msgs, moveit_msgs (+ object_recognition_msgs, octomap_msgs) | no |
  | `navigation` | nav2_msgs (+ geographic_msgs) | no |
  | `perception` | vision_msgs, pcl_msgs | no |

  Notes:
  - Packages outside ros2 core are pinned per distro in `UPSTREAM.lock` like the rest.
  - Adding a tier later is additive: new packages, nothing changes on the wire.
  - In 0.11: tiers `base` and `core`, both built by default. `manipulation`, `navigation` and `perception` are opt-in,
    and pinned in `UPSTREAM.lock` from the start, so that enabling them later only adds packages.
- **R5. Upstream file names:** `Time.idl`, `Duration.idl`, `String.idl`; the `_` renames are dropped. The script
  produces upstream names. Every IDL file gets an include guard derived from its path.
- **R6. No local changes to ROS types.** Needs that ROS does not cover belong in tcn types, which may embed ROS types.
  For example, HTA's A1 `StreamHeader` with an int64 time goes into `tcn_types`; `std_msgs/Header` keeps its upstream
  layout.
- **R7. Distro policy, so that later ROS releases do not force a break:**
  - The ROS tree tracks one LTS: Jazzy, until 2029, matching our Ubuntu 24.04 base.
  - Moving to the next LTS (Lyrical, together with a move to Ubuntu 26.04) is a scheduled ROS-only change. It can be a
    wire change for ROS types whose upstream definition changed, and it is announced like a break for those types
    only. Jazzy → Lyrical today: `Pose2D` removed, `PointField` constants added (§3.2).
  - Robots on another distro (Kilted, Lyrical) are reached through the type table: R3 holds the RIHS01 hash per

### 4.5 Fields nobody writes: removed in 0.11

**Rule.** A field of a kept struct is removed in 0.11 when no producer writes it. That covers two cases:
- the field is never set;
- the field is set only to a fixed value that does not come from data (an identity pose, `1.0`, `0`, `""`, an empty
  sequence, a per-producer constant).

**Code that reads such a field** gets a fix item in its project's list (§6). It reads a constant today, so the fix
is to stop reading the field, or to read the field that actually carries the information.
- Readers that only pass the value through, re-encode it or dump it for debugging still need updating, but they are
  not fixes.
- Under E1 (`@appendable`), a removed field can come back later as a trailing `@optional` member once a producer

## 5. Reorganisation

### 5.1 Problems with today's layout

- **`tcnart_msgs` is a grab-bag:**
  - the SQE protocol (`SpatialRelations.idl` 538 lines, `SIS.idl` 1,628);
  - media streams, tracking, XR, presence and parameters;
  - the shared math types (`Types.idl`, 295 lines).

  `pcpd_msgs` and the device packages depend on it, mostly for `Types.idl`.
- **A header collision.**
  - `tcnart_msgs/msg/SpatialRelations.idl` and `tcnart_msgs/rpc/SpatialRelations.idl` share a basename.
  - In the installed 0.10.7 package, `include/tcnart_msgs/rpc/SpatialRelations.h` is **byte-identical** to the msg
    header (same md5), so the rpc types never shipped. tcnart reported this in #37.
- **Generated code lands in the source tree** (`/include`, ignored by git). `CMAKE_BUILD_PARALLEL_LEVEL 1` keeps the
  generator runs serial.
- **Dependencies don't match the code:**
  - `tcnart_msgs` declares and links `geometry_msgs` but uses no geometry_msgs type; its own `Vector3`,
    `Quaternion` and `UUID` are used instead. The only ROS types our IDL uses are `std_msgs/Header` (32 places) and
    `builtin_interfaces/Time`.
  - `std_msgs` lacks its `builtin_interfaces` link.
- **Naming is mixed:**
  - conversation_msgs uses lower-case file names;
  - `module enums` exists only in the device packages;
  - there are three enumerator styles (#36 L3, #37 T16).
- **The repository root holds 23 `MIGRATION-*.md` files.**
- **Thin annotations and tests:**
  - The whole tree has one IDL annotation.
  - Only `PersonTracking` and `HumanPose` have round-trip tests, and they are off by default.
- **Tables maintained by hand:** enum ordinals and the request → key → reply table are mirrored in the contract
  library, the engine's `messages.rs` (registry at l. 3101-3201), the web controller (`packages/sqe/src/schemas.ts`),
  IVA (`crates/tcn-wire`), tcnart and HTA (#35 V3, #37 T17, #38 P3).

### 5.2 Proposal

- **O1. A new package `sqe_msgs`** for the spatial query engine protocol.
  - **Contents:** today's `tcnart_msgs/msg/SpatialRelations.idl` and `tcnart_msgs/rpc/SIS.idl`. The tracking structs
    `MarkerType`, `Marker` and `Target` are used both by `TargetTrackingMessage` (which stays in `tcnart_msgs`) and
    by SIS relation output (`SIS.idl:1618`), so they go to `tcn_types` (O2) and not here.
  - **Split by topic:**
    - `msg/Graph.idl`: SRGraph, SRNode, SREdge, the enums;
    - `msg/Transforms.idl`: SRTransform, SRIntrinsics, covariance;
    - (#35 N2's `SRFrameRef` lives in `tcn_types`, O2; N4's `SRRelationRef` stays here, in `Graph.idl`);
    - `rpc/Replies.idl`: R1/R2 header and status;
    - `rpc/Session.idl`: join/leave/info;
    - `rpc/Mutations.idl`;
    - `rpc/Streams.idl`: start/stop/status/plan/sample;
    - `rpc/Queries.idl`: graph/pattern/target/explain;
    - `rpc/Operator.idl`: txlog/fragments/operator mutation;
    - `rpc/Calibration.idl`.
  - Modules `sqe_msgs::msg` / `sqe_msgs::rpc`. Whether the `SR`/`SIS` prefixes stay is #35 D3/G1.
  - **Why now:**
    - #35 changes nearly every one of these types, and every SQE peer regenerates in lockstep.
    - The wire type names (`application/cdr;tcnart_msgs::msg::SRGraph;…`) change anyway with #35 V1 and E1.
    - Doing the move later would be a second break of the same kind.
  - The contract library in `src/sqe` stays and depends on `sqe_msgs` and `tcn_types` only.
- **O2. A small foundation package `tcn_types`** for what everything includes:
  - `Geometry.idl`: Vector2/3, Quaternion, RigidTransform, Ray, ViewPose; #35 E1's `SRCovariance6`/`SRCovariance3`;
    `CoordinateSystem`/`CoordinateAxis`.
  - `Ids.idl`: UUID.
  - `Frames.idl`: #35 N2's `SRFrameRef`. It is here, not in `sqe_msgs`, because #38 A1's `StreamHeader.frame` embeds
    it in every stream message (SQE answer on O-D1).
  - `Tracking.idl`: `MarkerType`, `Target` (shared by pose streams and SQE output; `Marker` is removed by F2), and
    #37 T7's `SISTargetInfo { uint32 id; string name; SISTargetKind kind; }` for the typed tracker descriptor. SQE and
    HTA both chose T7 over #38 A2's `target_names`, which HTA withdrew: explicit ids, because marker, ART and NDI ids
    are not dense.
  - `Time.idl`: the clock-domain definition, and #38 A1's `StreamHeader` if accepted.
    - **Decided (C-D1):** `ClockDomain { string id; ClockKind kind; }`, used in descriptors, `StreamHeader` and SQE
      outputs.
      - `id` follows #37 T10's rules: one alphabet defined in this file, and `""` = the deployment clock.
      - Equality is on `id` alone; `kind` is informational.
      - Agreed by the SQE, tcnart and HTA. HTA had withdrawn the struct only to avoid a conflict, and `kind` is what
        its A1 wanted.
      - The web controller is fine with either form, given a defined display form: the display form is `id`.
    - The descriptor's domain stays authoritative for routing (SQE).
    - A1 keeps the optional `device_time_ns` next to the capture time.
  - `Camera.idl`: the one `CameraIntrinsics` that #35 E2, #37 T4/T8 and #38 A3 each ask for.

  `tcnart_msgs`, `pcpd_msgs`, `sqe_msgs` and `conversation_msgs` (if it needs any) depend on `tcn_types`, not on
  each other.
- **O3. Keep the names `tcnart_msgs`, `pcpd_msgs` and `conversation_msgs`.** Renaming them would change every
  consumer's includes, namespaces, generated C#/TS/Rust and every wire type name, with no gain on the wire. Within
  them:
  - **Unique basenames per package**, so that no name appears in both `msg/` and `rpc/`.
  - **`Types.idl` is dissolved.** The shared parts go to `tcn_types` (O2) and the SQE parts to `sqe_msgs` (O1). The
    media enums (`SensorType`, `VideoPixelFormat`, `VideoImageCompression`, `VideoH26xProfile`, `AudioAACProfile`)
    go to `tcnart_msgs/msg/MediaTypes.idl`. `Handedness` goes next to HandTracking, and `XRGazeSpaceType` next to
    EyeTracking.
  - **conversation_msgs:** PascalCase file names, prefixed enumerators (#36 L3, #37 T16), and the encapsulation
    header (E4).
  - **The parameter RPC** (`Requests.idl`, renamed `Parameters.idl`) moves to `pcpd_msgs` in 0.11.0, next to
    `ServiceController.idl`. Both are the generic service surface that tcnart, HTA and IVA all serve (decided, O-D2).
    For HTA it is a mechanical rename in 24 files.
- **O4. The ROS 2 tree** is generated by `tools/ros2/refresh.py` (R2). It has upstream names, a lock file, tiers
  (R4) and the type table (R3).
- **O5. An IDL style guide,** `docs/idl-style.md`, checked by a lint in CI:
  - PascalCase file names, unique within a package;
  - one include guard per file, derived from its path;
  - `@appendable` written explicitly on every tcn struct; `@final` on ROS types;
  - `@optional` instead of flag pairs, sentinels or "empty means absent" (#35 P3);
  - enumerators named `TYPE_NAME_VALUE`, with the first one `…_UNKNOWN`/`…_NONE` (E6);
  - no `module enums`;
  - each top-level message documents its key or topic and its encoding;
  - in zero-copy messages the payload is the last member (#37 T8, #38 A8).
- **O6. Build:**
  - Generate into `${CMAKE_BINARY_DIR}`, and drop the forced serial build.
  - Link dependencies exactly.
  - Generate the conan `package_info()` components from the same table CMake uses.
  - Pass `-de appendable` explicitly.
  - Keep the toolchain at fast-dds-gen 3.0.0 / fast-cdr 2.0.0 (§2.1). Moving fast-cdr to 2.3.x is optional.
- **O7. Generated tables,** installed under `share/tcn_schema/`:
  - `enums.json`: every enum with its ordinals;
  - `types.json`: every top-level type with:
    - its fully qualified wire type name, package and encoding family (XCDR2 or ROS XCDR1);
    - member order, extensibility, `@optional`, bounds and union labels (the web controller's list);
    - through annotations, its key and its request/reply pair (#35 V3).

    Generated **from the IDL**, not from a usage scan. tcnart notes that the scan behind the type appendix misses
    uses that name only enumerators or members.
  - `ros2_types.json` (R3).

  The contract library's mirrored enums, the engine's wire-name list, the web controller's schemas, IVA's `tcn-wire`
  mirrors and tcnart's Unreal ordinals are generated from these tables, or at least checked against them in each
  consumer's CI.
- **O8. Tests,** built by default in CI:
  - a generated XCDR2 round-trip test for every tcn top-level type;
  - an XCDR1 round-trip for every ROS top-level type;
  - the appendable check: a decoder for the older version reads a longer payload.
  - **Golden byte files** for a few types per package under `test/golden/`, so that the Rust, TS, C# and Python codecs
    can test against the same bytes.
- **O9. Documentation:**
  - Move the MIGRATION files to `docs/migration/`, keeping a root `MIGRATION.md` index.
  - Move dated proposals to `docs/proposals/`.
  - Rewrite the README around the packages after 0.11.

## 7. Order of work

**Scope rule** (proposed by tcnart, with the goal of no further break soon):
- **0.11.0** carries every **reshape**: removals, renames, moves, changed field types, extensibility, enum
  renumbering, and redesigns of existing types (for example HumanPose).
- **New types, new union cases and new enumerators** can follow in **0.11.x**, as additive releases. That relies on
  E6 (unknown enumerators and union cases) and E8 (missing members take defaults) being normative and implemented by
  every codec in 0.11.0.
- Additive items from #36–#38 may still land in 0.11.0 when they are ready; nothing forces them into it.
  Examples: #36's PlaybackEvent and face animation, and #38's typed RPC messages.

| Step | Work | Gate |
|---|---|---|
| 1 | Decide the §8 items; teams answer §6 | review of this PR, #35-#38 |
| 2 | Toolchain and layout: O6 build, O5 lint, O7 tables, O8 test harness with golden files; `tools/ros2/refresh.py` with R1-R7 | CI green with today's types, unchanged on the wire (still XCDR1) |
| 3 | Moves and deletions: O1-O3, groups A and B; files renamed and split **before** the #35-#38 IDL edits, so those land in the new files | moves only, no field changes; tables regenerated |
| 4 | E1-E9, the field removals of §4.5, plus the type changes of #35-#38 | round trips and golden files; each project's §6 fix list done |
| 5 | `0.11.0-rc1` (as #37 asks); consumers regenerate and report | each consumer's CI against the golden files |
| 6 | `0.11.0` and the lockstep cut-over (#35 §9) | |

- step 2: about three days, of which the ROS script is one;
- step 3: one to two days;
